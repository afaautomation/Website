# Backend Integration Handoff — Kompetenzen Job Listings

This folder holds the front-end pages for the Jobs section of the Kompetenzen
website. Everything here is static HTML/CSS/JS — there's no backend yet.
Every spot that needs a real server connection is marked in the code with a
`TODO(backend)` comment, and listed below with the exact location and the
data shape it sends/expects.

## Files in this folder

| File | What it is |
|---|---|
| `jobs.html` | Public-facing **Job Listings** page (candidate view) — job cards with category filters, an announcement banner with a "Notify Me" popup form |
| `admin.html` | **Internal-only** HR tool for posting new job listings — gated behind a staff key, currently saves drafts to the browser only |

## What needs to be wired up

### 1. `jobs.html` → "Notify Me" event signup form
- **Where**: `submitToBackend()`, ~line 1495 (search `TODO(backend)`)
- **Now**: logs the payload to the console and resolves a fake success
- **Needs**: `POST` to an event-signup endpoint (e.g. `/api/event-signups`), persisted to the DB and fed into the Excel export pipeline
- **Payload shape**:
  ```json
  {
    "name": "string",
    "phone": "string",
    "email": "string",
    "interest": "career-fair | job-alerts | training | other"
  }
  ```

### 2. `jobs.html` → login / auth guard
- **Where**: lines 9–11, top of file (inline script, runs before page renders)
- **Now**: checks `localStorage.getItem('token')`; if missing, redirects to `index.html#jobs-auth`
- **Needs**: a real `index.html` with a working login flow that sets that session token (or whatever auth mechanism you settle on — cookies/JWT also fine, just update the guard to match)

### 3. `admin.html` → staff login
- **Where**: `STAFF_KEY` constant, ~line 545 (search `TODO(backend)`)
- **Now**: a hardcoded passcode (`kompetenzen-hr-2026`) checked entirely client-side — visible to anyone who views the page source, **not real security**
- **Needs**: replace with backend-issued staff/HR authentication (session or JWT) before this page is exposed publicly. Until then it should stay off any public host or behind something like HTTP basic auth at the server level.

### 4. `admin.html` → "Post a new job listing" form
- **Where**: the IIFE around `STORE_KEY`, ~line 580 (search `TODO(backend)`)
- **Now**: saves entries to `localStorage` (`kompetenzen_hr_draft_jobs`) with a view/delete UI — purely a local draft, nothing reaches a server
- **Needs**: `POST /api/hr-jobs` → insert into a new `hr_jobs` table, also feeding the Excel export pipeline
- **Payload shape**:
  ```json
  {
    "title": "string",
    "category": "tech | hr | sales",
    "company": "string",
    "location": "string",
    "jobType": "full-time | contract | part-time | remote",
    "experience": "string, free text — e.g. '3-5 Years'",
    "salary": "string, free text — e.g. 'INR 8L - 14L / year'",
    "skills": "string, comma-separated — e.g. 'Python, FastAPI, PostgreSQL'",
    "description": "string",
    "applyUrl": "string (URL) — external application link candidates are redirected to for that specific role"
  }
  ```

### 5. `jobs.html` → rendering live listings
- **Now**: The jobs page reads dynamic listings from `localStorage` (`kompetenzen_hr_draft_jobs`), generated by `admin.html`, and appends them alongside the hardcoded HTML job cards in the `#jobs-grid` container. It also dynamically updates the filter counts on page load.
- **Needs**: Once a database is introduced, replace `localStorage` checks in both `admin.html` and `jobs.html` with real API calls:
  - `admin.html` should POST to `POST /api/hr-jobs`.
  - `jobs.html` should GET from `GET /api/jobs`.
  - Keep `category` values restricted to `tech` / `hr` / `sales` to match the existing filter buttons and schema.

## A few things worth knowing
- All colors/fonts/spacing are CSS custom properties in `:root` at the top of each `<style>` block (`--ink`, `--blue`, `--blue-deep`, `--blue-soft`, `--cream`, `--paper`, `--line`, `--radius`, `--maxw`) — reuse them if the UI grows so everything stays visually consistent.
- `admin.html` is intentionally **not linked** from `jobs.html` — it's meant to stay an internal tool reachable only by a direct URL (and eventually proper login), not discoverable from the public site.
- The Excel export mentioned for both forms above can likely share one pipeline — both payloads are flat objects that map cleanly to spreadsheet rows.
